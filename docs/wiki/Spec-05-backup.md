# 05. バックアップと復元

## 方針

常駐プロセスを持たない。実行したい時だけコンテナを起動し、終了後に破棄する。

`itzg/mc-backup` が RCON 経由で `save-off` → `save-all` → アーカイブ作成 → `save-on` を内部的に行うため、セーブ制御を自前で書く必要がない。書き込み中のワールドをコピーして壊れたアーカイブを作る、という失敗を避けられる。

## 二重化

```text
mc-server:/home/ubuntu/minecraft/data
        │
        │ itzg/mc-backup (使い捨てコンテナ)
        ▼
    backups/*.tgz  ── 直近 7 世代のみ保持
        │
        ├─ rclone copy ────────► Cloudflare R2         (一次コピー / 別事業者)
        └─ oci os bulk-upload ─► OCI Object Storage    (二次コピー / 同一事業者)
```

| | ローカル (VM) | Cloudflare R2 | OCI Object Storage |
| --- | --- | --- | --- |
| 役割 | 直近の即時復元 | 一次コピー | 二次コピー |
| 保持 | 7 世代 (`backup_keep_generations`) | 30 日 (`backup_remote_keep_days`) | 30 日 (ライフサイクルポリシー) |
| 無料枠 | ブートボリューム 100GB の一部 | 10GB / 月100万リクエスト | 20GB / 月5万リクエスト |
| 認証 | - | S3 互換キー (`rclone.conf`) | インスタンスプリンシパル |
| 事業者 | OCI | Cloudflare | OCI |

### なぜ R2 を一次にするのか

**サーバーとバックアップを別事業者に分けられる**ことが理由である。両方 OCI に置くと、アカウント停止やリージョン障害で同時に失われる。リクエスト数の枠に余裕がある (月100万回 vs 5万回) ことも R2 を主に使う理由になる。

OCI 側を併設するのは、R2 の認証情報が VM 上の `rclone.conf` にあるため、VM が侵害された場合に R2 のオブジェクトも削除されうるからである。OCI 側はインスタンスプリンシパルで**バケット1つへの権限に限定**されており、かつ削除はライフサイクルポリシーが行うため、経路が異なる。

### なぜ `rclone sync` ではなく `copy` なのか

`sync` はローカルに存在しないオブジェクトをリモートから削除する。ローカルは7世代しか持たないため、`sync` だと R2 も7世代に切り詰められる。それ自体は一貫した方針だが、**ローカルの世代削除のバグがそのままクラウドのバックアップ消失に波及する**。

`copy` (追加のみ) にして、リモートの世代管理は別の仕組みに持たせる。

| 保存先 | リモートの世代管理 |
| --- | --- |
| R2 | `backup.sh` の `rclone delete --min-age 30d` |
| OCI | `terraform/storage.tf` のライフサイクルポリシー (宣言的) |

OCI 側を Terraform のライフサイクルポリシーにしているのは、**`backup.sh` が失敗しても保持期間が守られる**ためである。

## 実行

### 手動実行

```bash
ssh ubuntu@mc-server
~/minecraft/backup.sh
```

平常時は `docker ps` に `mc` (と `exposure_mode=playit` なら mc-router・playit) しか表示されない。バックアップ中だけ一時的にコンテナが現れ、`--rm` により終了後に自動削除される。イメージ本体 (数十MB) はホストに残り、次回の起動が速くなる。

### mc が起動していることが前提

`docker run --network container:mc` で `mc` のネットワーク名前空間を共有して RCON に繋ぐため、`mc` が停止していると実行できない。そのまま走らせると `network container:mc not found` という分かりにくいエラーになるので、`backup.sh` の先頭で `docker inspect` を見て、止まっていれば起動コマンドを示して終了する。

`mc_router_auto_scale = true` にして無人時に mc を停止させている場合は、バックアップ前に `docker compose up -d mc` が必要になる。既定 (`false`) では mc は常時起動しているので問題にならない。

### 自動化していない理由

自動化そのものは systemd タイマーを追加するだけで、常駐プロセスは増えない。していないのは次の理由である。

- ワールドが育つ前は取る意味が薄く、育った後は世代管理の設計が必要になる
- 「いつ取ったか」を自分が把握している方が、復元時に迷わない
- 遊ぶ前後に手で叩く運用で、実用上の RPO が足りている

自動化する場合は [06. 運用・保守](Spec-06-operations) の将来の拡張を参照。

### RPO / RTO

| 指標 | 値 | 根拠 |
| --- | --- | --- |
| RPO (許容データ損失) | 最後に手動実行した時点まで | 手動運用のため。遊ぶ前後に実行する想定 |
| RTO (復旧目標時間) | ローカルに世代があれば 5〜10 分 | `restore.sh` の展開時間 |
| RTO (R2 から取得する場合) | + ダウンロード時間 | ワールドサイズ次第 |

事業システムではないため、RPO を短縮するより「復元が確実にできる」ことを優先している。

## 復元

```bash
scp scripts/restore.sh ubuntu@mc-server:~/
ssh ubuntu@mc-server
~/restore.sh              # R2 の一覧を表示して選ばせる
```

`restore.sh` の設計上のポイント。

| 段階 | 内容 | 理由 |
| --- | --- | --- |
| 1. 一覧表示 | `rclone lsl` で候補を出す | ファイル名を覚えていなくても復元できる |
| 2. 検証 | `tar -tzf` で中身を確認 | **壊れたアーカイブで上書きしない** |
| 3. 確認 | 実行内容を表示して y/N を問う | 誤爆防止 |
| 4. 退避 | `data` → `data.broken.<日時>` | **現在のワールドを削除しない**。復元後に問題があれば戻せる |
| 5. 展開 → 起動 | | |

退避したディレクトリは自動削除しない。起動を確認してから手で消す。

### 構築直後に一度試す

**バックアップは復元できて初めて機能する。** 受入試験 V-18 として、構築直後に一度通すことを必須にしている。四半期ごとの復元テストも定期作業に含めている ([06. 運用・保守](Spec-06-operations))。

## バックアップ対象

| 対象 | 含まれるか | 備考 |
| --- | --- | --- |
| ワールドデータ | ○ | `./data` 配下 |
| `server.properties` | ○ | `./data` 配下 |
| プラグインとその設定 | ○ | `./data/plugins/` 配下。LuckPerms の権限データも含む |
| ホワイトリスト / OP | ○ | `./data` 配下だが、正は `terraform.tfvars` 側 |
| `docker-compose.yml` | ✕ | Terraform から再生成できる |
| `.env` | ✕ | Terraform から再生成できる |
| VM 自体 | ✕ | Terraform から再作成できる |

**VM が失われてもワールドがあれば戻せる**という設計である。構成はコードから、データはバックアップから復元する。

## 圧縮方式

デフォルトは tar 方式で、世代ごとにほぼフルサイズになる。容量が気になる場合は rsync 方式 (差分) に変更できる。

```bash
docker run --rm --network container:mc \
  -e BACKUP_METHOD=rsync \
  ... itzg/mc-backup backup now
```

既定を tar にしているのは、1ファイル1世代で完結し、復元時に依存関係を考えなくてよいためである。

## 注意点

| 項目 | 内容 |
| --- | --- |
| `--network container:mc` | `mc` コンテナのネットワーク名前空間を共有する指定。これにより bridge / host のどちらの `exposure_mode` でも `localhost:25575` で RCON に到達する |
| バケット削除 | OCI は空でないバケットの削除を拒否するため、中身がある限り `terraform destroy` は自然に失敗して止まる |
| OCI CLI | 公式 install.sh は対話が入るため、cloud-init では `/opt/oci-cli` に venv + pip で導入している |
| `--no-overwrite` | 同名オブジェクトを上書きしない。アーカイブ名にタイムスタンプが入るため衝突しない前提 |
